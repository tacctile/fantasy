## Build (7 new files, 3 edits, one fold, items built in checklist order)

1. **`services/luck.ts`** (items 1, 2, 4). `computeLuck(rows, rosterNames, playoffWeekStart, standingsWins?)` is the pure core; `getLuck(db, leagueId)` is the client-injected getter (matchups incl. `native_matchup_id`, `league_config.roster_settings_raw`, `standings.wins`, roster names via the shared `fetchRosterNames`). Expectation = per-week `(beaten + tied/2) / opponents`, summed. Actual = recomputed pairing, ties as half-wins on both sides so the two figures are directly comparable (`actualWinEquivalent = W + T/2`). Per team it returns the week-aligned series the drill-down needs: points, opponent points, result, week share, running cumulative luck. A lone posted score in a week rates NOBODY — `allPlayShare` returns null rather than crediting a free 1.000 to the only team that has posted mid-Sunday.
2. **`services/luck.test.ts`** (item 3) — 27 tests, one describe block per case the build file names: ties (head-to-head and all-play), byes/unpaired groups, incomplete weeks, zero completed weeks, odd/even team counts; plus cumulative accumulation, the standings cross-check, and the recording-fake-client column boundary (asserts exactly which four tables and which columns are read, and that `share_token`/`owner_id`/`*` never appear).
3. **`components/luck/luck-notes.ts`** — the four disclosure lines in one place so the three views can never disclose different things about the same numbers.
4. **`components/luck/luck-ranked-chart.tsx`** (item 5) — one diverging bar per team about a shared centre line, both arms on one `maxMagnitude` scale, diverging tokens only (never the categorical ramp — this chart encodes polarity, not identity), every bar labelled `"W-L actual / X.X-Y.Y expected"`. On a narrow viewport the record label RELOCATES under the team name rather than being dropped: the item's "reads without a legend" requirement is the point of the label, so hiding it at a breakpoint would defeat it.
5. **`components/luck/luck-drilldown.tsx`** (item 6) — per-week diverging bars (a week's luck is a discrete event) plus a cumulative line with a zero reference (a running total genuinely is continuous). Neither re-derives anything the service computed.
6. **`components/luck/luck-shell.tsx`** + **`app/(admin)/leagues/[leagueId]/luck/page.tsx`** + **`loading.tsx`** — composition and route, mirroring the Score Trends resilience shape (`getLeagueContext` → 404 / header survives; `getLuck` through `settleQuery` → `SectionUnavailable`). Disclosures render ABOVE any chart, because they qualify every number below them. The drill-down REPLACES the ranked view rather than sitting beside it (item 6 requires a separate view; stacking invites reading a per-team bar as a league one), with the ranked list underneath as the way back. `loading.tsx` deliberately uses no `ChartSkeleton` — this section's primary view is a row list, and a bar-chart placeholder would promise a shape that never arrives.
7. **`components/spectator/spectator-luck-summary.tsx`** (item 7) — separately built, imports only `components/charts/format` and the luck service's types. Inlines its own team naming rather than importing the admin surface's `teamLabel`.
8. **`components/luck/luck-render.test.ts`** — 31 tests rendering the section over a 10-team × 14-week season constructed to CONTAIN real luck (fixed pairings against rising scoring, so mid-table teams win or lose against the field).
9. **Edits:** `admin-sidebar.tsx` — `Luck Tracker` moved from `FUTURE_NAV` to `PRIMARY_NAV` at `/luck`. `spectator-markup.test.ts` — the admin-directory regex in the import-graph guard extended to `luck|score-trends`, because Wave 5's admin section directories were not covered and a spectator import of either is the same boundary violation as importing the admin dashboard. `05_eye_candy.md` — items 51–57 `[x]`, item 57 annotated component-only.

**Disclosed judgment calls:** (a) the luck components import `teamLabel` from `components/score-trends/` rather than growing a third copy of the same three-line convention — same section family, identical structural props type; the SPECTATOR component deliberately does not, and inlines instead, to keep the separate-rendering-path rule true by construction; (b) `round3` for win shares (a 1/9 all-play share is 0.111, not 0.11) while records/deltas stay `round2`; (c) an anomalous matchup group (size ≠ 2) is treated as no-game rather than a forced pairing, matching `getMatchups`' shipped posture; (d) the ranked view filters to teams with ≥1 rated week, so an unsynced roster doesn't occupy a row claiming 0.0 luck.
