## Declared wiki silence (stated at decision time, before the code was written)

**Flex-label eligibility.** No wiki page specifies which positions a given flex label admits. `sleeper-api/league-endpoint` names the labels and records that the set is not exhaustively documented; `league-mechanics/flex-spot-configuration` covers which position tends to WIN a flex and explicitly declines to adopt numeric allocations. A retrospective attribution of an already-played week needs eligibility, not tendency — genuinely different questions. So `FLEX_ELIGIBILITY` encodes the corroborated conventional meanings (`FLEX` → RB/WR/TE, `SUPER_FLEX` → QB/RB/WR/TE, `REC_FLEX` → WR/TE, `WRRB_FLEX` → RB/WR) and — the part that actually matters — an **unrecognised** `*FLEX*` label is treated as open to every position rather than dropping its points on the floor. Unknown labels degrade toward inclusion, and a unit test pins that behaviour so a future IDP or custom label can't silently lose scoring.

## The schema finding that shaped the whole fold

`player_scores` records **that** a player started (`was_starter`) and **never which slot he filled**. There is no per-week lineup-slot record anywhere in the schema — `roster_players.slot` is a current starter/bench/reserve/taxi snapshot, not a per-week positional assignment. `components/dashboard/matchup-card.tsx` already documents the same gap from the other direction ("slot-by-slot pairing impossible — was_starter only, no historical slot attribution").

This is a **permanent ceiling, not a v1 shortcut**: no platform payload carries the information, so it cannot be fixed by a later sync change. It was surfaced to Nick as the fold's first Clarify question rather than resolved unilaterally, and the chosen reconstruction (dedicated slots first, highest scorer per position, surplus to flex) is disclosed on the surface itself.

## Disclosed judgment calls

- **Colour on the single-team bars is position identity, not polarity** — the opposite of the luck chart's choice, and deliberately so: that chart's dimension IS polarity, this one's IS position. Polarity is still encoded twice (side of the centre line, signed colour-coded delta), so it never depends on colour alone.
- **Unmapped is excluded from the bars but included in the table.** It has no league-average meaning, so plotting it against the same centre line would invent a comparison; leaving it out of the table entirely would make its points un-inspectable.
- **Heatmap shade opacity is floored at 0.08 and capped at 0.55** so a mid-table cell still reads as a cell and the printed number never loses contrast. The number is always the real total, so a reader who ignores colour entirely loses nothing.
- **Greedy dedicated-first attribution has a known, stated bias:** it always assigns the higher scorer to the dedicated slot, so it will differ from the platform's lineup screen in the specific case where a lower-scoring RB was actually started in the FLEX. Recorded in `known_issues`.
- **The `players(position)` embed is this wave's first PostgREST relation read.** It is parsed defensively (object OR array OR null all degrade to "unmapped"), so a shape surprise on the real database renders an honest Unmapped bucket rather than throwing mid-render.
